# 使用场景

先确定用户要一份文档，还是一段回复。同样是解释报错，回复不套用文档的硬性字数上限。
下面是写法示例，不是针对真实系统的诊断或操作授权。
所有场景都保留错误原文、代码、数字、限制条件、安全警告和操作确认。

## 报错说明

先说已知原因，再解释影响和下一步。不知道原因时，直接说证据不足。
把原始错误放在代码块中，包含其中的英文标点、路径和大小写。
建议的排查步骤与已经确认的结论要分开。

已知事实：日志显示连接池等待超时；尚未检查连接释放代码。

```text
连接池等待超时，但这条日志不能确定连接是否泄漏。检查请求结束后是否释放连接。

原始错误：TimeoutError: pool exhausted after 5000ms!
```

不要把这条日志直接改写成“连接泄漏了”，也不要承诺一个补丁必然解决问题。
若任务要求逐字保留整段错误，原样引用整段，不只摘录最后一行。

## 发布说明

先写用户能感知的变化，再写影响范围、兼容性和升级要求。
多个独立变化可以用列表；单个修复用一段话即可。
没有实测数据时，不补充性能、稳定性或用户受益数字。

已知事实：1.2.0 修复重复导出；旧配置可用；无需迁移数据。

```text
1.2.0 修复了重复导出的问题。旧配置仍然可用，无需迁移数据。
```

若原文含破坏性变更或回滚限制，不能为缩短发布说明而删掉。

## 事故报告

先写影响和当前状态，再写时间线、已知原因和后续措施。
长报告用标题区分主题；短更新用段落，不给每一句加标题。
保留日期、时区、持续时间、影响范围和不确定性。把事实与假设分开。

已知事实：09:10 至 09:18（UTC+8）导出接口返回 503；回滚后恢复；原因仍在调查。

```text
09:10 至 09:18（UTC+8），导出接口返回 503。团队回滚版本后，接口恢复。事故原因仍在调查。
```

不把“回滚后恢复”改成“证实新版本是根因”。原文没有负责人和完成日期时，不擅自添加承诺。

## 提交信息

保留项目约定的前缀、范围、issue 引用和尾注。主题写动作与对象，不写重要性。
正文只解释必要原因、影响或兼容性。用户只要文案时，不运行 git，也不自行提交。
仓库已有固定格式时沿用格式，不为简化而删除机器读取的字段。

已知事实：修改了请求结束后的连接释放逻辑；项目使用 `fix(pool):` 前缀。

```text
fix(pool): 请求结束后释放连接
```

不要写成“全面优化连接池底层逻辑”，也不要把未运行的测试写成已通过。

## 危险操作的表达

先保持原警告与确认原文完整，再处理周围的解释。缺少危险操作所需的确认时，不把改稿任务当执行授权。
警告中的“可能”代表风险不确定性，不能为了情态词规则删去。
如果原文只有“此操作有风险”却没有说明后果，标记信息不足，不凭空补出风险等级。
